# Building and releasing the mobile app

`mobile/flutter_app/` is the farmer client. This document is the only place that describes how to
produce an installable artefact, what is verified, and what is **not** done.

## 1. Toolchain (exact versions used here)

| Component | Version | Notes |
| --- | --- | --- |
| Flutter | 3.47.6 (stable) | Dart 3.13.5; `pubspec.yaml` requires Dart ≥ 3.6 |
| JDK | Temurin 21 LTS | Gradle 8.x + Android Gradle Plugin need ≥ 17; JDK 21 is what CI uses |
| Android SDK | platform 36, build-tools 36.0.0, platform-tools 37.x | `minSdk 23` (required by `flutter_secure_storage`'s `EncryptedSharedPreferences`), `targetSdk`/`compileSdk` from the Flutter default |
| Gradle | wrapper, `org.gradle.jvmargs=-Xmx1536m` | tuned so a 2 GB machine can build |

Set the environment before running any Flutter command:

```bash
export JAVA_HOME=<jdk-21>
export ANDROID_HOME=<android-sdk>
export PATH=$FLUTTER_HOME/bin:$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:$PATH
flutter doctor -v          # Android toolchain must be a green check
```

On a machine that has never built Android, `flutter doctor --android-licenses` must be accepted
first. `scripts/` in this repository does **not** install Flutter: the backend bootstrap script is
about Python, PostgreSQL and Redis.

## 2. Verify, then build

```bash
cd mobile/flutter_app
flutter pub get
flutter analyze                 # must report "No issues found!"
dart format --output=none --set-exit-if-changed lib test
flutter test                    # 67 tests: l10n table, formatters, models, widgets, screens
flutter build apk --debug --target-platform android-arm64
```

Artefacts land in `build/app/outputs/flutter-apk/`. A copy of the debug APK this repository's
environment produced is committed under `artifacts/mobile/` with a SHA-256 checksum, so the build
result is inspectable without rebuilding:

| Artefact | Size | SHA-256 | Signed with |
| --- | --- | --- | --- |
| `digital-village-0.1.0-debug-arm64.apk` | 87 MB | `a50a1437…48a5f6ee` | Android debug key (`CN=Android Debug`) |

The APK above carries the server-connection work from §4a–4d: the in-app server panel is reachable
**before sign-in**, a debug build no longer restricts cleartext HTTP to the emulator alias (which is
what blocked a phone pointed at a LAN address), and a probe that gets no answer now names the
transport-level cause and the next step instead of stopping at "No answer". `aapt2 dump xmltree --file
res/xml/network_security_config.xml` on the APK shows `base-config cleartextTrafficPermitted=true`
(the debug source set), while a release build keeps the strict `main` policy.

Debug builds are signed with the debug keystore of the machine that built them, so an APK built
elsewhere (or a keystore regenerated by a fresh toolchain) has a different certificate. Android
refuses to update across different signing keys — uninstall the previous debug build before
installing a new one ("App not installed" / `INSTALL_FAILED_UPDATE_INCOMPATIBLE`).

The checked-in APK contains the generated icon set and splash from §3b: `aapt2 dump badging` reports
`application-icon-160..65534: res/mipmap-anydpi-v26/ic_launcher.xml`, and
`assets/flutter_assets/assets/branding/app_icon.png` is bundled for the Flutter splash.

The debug APK is not shrink-wrapped and includes the JIT kernel snapshot (hence the size); it is
signed with the shared Android debug key and has `android:debuggable` set, so it must never be
distributed to farmers.

### Building on a small machine

The defaults in `android/gradle.properties` are tuned for a machine with ~2 GB of RAM
(`-Xmx1024m`, `org.gradle.daemon=false`, `workers.max=1`, Kotlin compilation in-process). On a box
that also holds the Dart tool (about 300 MB while Gradle runs) that ceiling is still too high: the
kernel OOM killer takes the Gradle daemon mid-build and Gradle reports "the daemon disappeared
unexpectedly". Capping the daemon at `-Xmx672m` with `MaxMetaspaceSize=384m` — plus
`org.gradle.vfs.watch=false` and `-XX:TieredStopAtLevel=1` — is what makes a debug build complete
here, in about 1.5–3 minutes, to an 87 MB APK.

```bash
# build-local Gradle settings (GRADLE_USER_HOME/gradle.properties), ~2 GB machines
org.gradle.jvmargs=-Xmx672m -XX:MaxMetaspaceSize=384m -XX:ReservedCodeCacheSize=64m \
  -XX:+UseSerialGC -XX:TieredStopAtLevel=1
org.gradle.workers.max=1
org.gradle.parallel=false
org.gradle.daemon=false
org.gradle.vfs.watch=false
kotlin.compiler.execution.strategy=in-process
```

A CMake subproject (`:jni`, from a plugin's native code) also wants metaspace: `MaxMetaspaceSize`
must be at least 384 MB, and without `-XX:TieredStopAtLevel=1` the daemon dies with a bare
`> Metaspace` failure during `:jni:configureCMakeDebug`. A cold Android SDK additionally makes Gradle
auto-install platforms 34 and 35 mid-build, which is the heaviest moment of the whole run — install
them once (`sdkmanager "platforms;android-34" "platforms;android-35"`) before building, or expect to
retry.

Because the Dart step and the Gradle step then run one after the other rather than nested, pre-warm
the Dart side first — it finishes in ~20 s on its own:

```bash
flutter assemble -dTargetPlatform=android-arm64 -dBuildMode=debug \
  -dTargetFile=lib/main.dart --output=build/flutter_app_bundle debug_android_application
```

That is enough for `--debug`. `--release` additionally runs the AOT compiler (`gen_snapshot`), which wants
about 800 MB on its own: use a machine with at least 4 GB, or build release in CI (where the
standard `-Xmx8G` settings are fine). Build one ABI at a time on a constrained machine:

```bash
flutter build apk --release --target-platform android-arm64
flutter build appbundle --release                     # Play Store artefact
```

If the build appears to stall (Gradle at a few percent CPU for minutes), the Dart kernel compile is
starved, not broken — it runs *inside* the Gradle build while Gradle holds its own heap. Pre-warming
it without Gradle in the way, then rebuilding, fixed this here:

```bash
flutter assemble -dTargetPlatform=android-arm64 -dBuildMode=debug \
  -dTargetFile=lib/main.dart --output=build/flutter_app_bundle debug_android_application
flutter build apk --debug --no-pub --target-platform android-arm64     # ~170 s here
```

Resources can be validated without Gradle at all, which is how the icon/splash changes were checked:

```bash
aapt2 compile --dir mobile/flutter_app/android/app/src/main/res -o /tmp/res.zip   # 18 resources, no errors
```

## 3. Release signing — the key does not exist in this repository

`android/app/build.gradle.kts` reads `android/key.properties` when it is present:

```properties
storeFile=/absolute/path/to/upload-keystore.jks
storePassword=…
keyAlias=upload
keyPassword=…
```

Create it once per product, and keep it out of the repository (`.gitignore` already excludes
`key.properties`, `*.jks` and `*.keystore`):

```bash
keytool -genkeypair -v -keystore ~/upload-keystore.jks -storetype JKS \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Without that file, `flutter build app-release.apk` and `flutter build appbundle` fall back to the
**debug** key and print a Gradle warning. That fallback exists so `flutter run --release` works on a
developer machine; a debug-signed release build must not be uploaded to Play. No keystore, no
Play Console account, and no upload exist for this project — the commands above are the documented
path, not a claim that a release build was produced.

Release builds also need the production API address baked in (see §4) and, for Play, an App Bundle:

```bash
flutter build appbundle --release --dart-define=API_BASE_URL=https://api.example.org
```

`scripts/make_branding.py` draws the mark (a seedling over a soil arc on the theme green
`#2E6E3F`) with Pillow and writes every size the app needs, so the artwork is reviewable code


| Output | Purpose |

| `android/app/src/main/res/mipmap-{m,h,xh,xxh,xxxh}dpi/ic_launcher.png` | legacy launcher icon (48–192 px) |

## 4. Pointing the app at a backend

Resolution order in `lib/core/config.dart`:

1. `--dart-define=API_BASE_URL=https://api.example.org` (compile-time, wins);
2. an address saved from the in-app **server panel** (persisted in the platform keystore);
3. the platform default: `http://10.0.2.2:8000` on Android (the emulator's alias for the host
   machine), `http://localhost:8000` elsewhere.

All API requests go to `<base>/api/v1`; the two probes below go to `<base>/health` and
`<base>/ready`, which live outside the versioned prefix.

### 4a. The in-app server panel

`ServerSettingsSheet` (`lib/widgets/server_settings.dart`) is reached **before sign-in** — the
address row under the login form, plus a globe action in the login app bar — and again from
**Profile → Developer options → Test connection**. It shows the address currently in force, lets it
be edited, saves it, and then really calls `/health` and `/ready` on it, reporting the status code,
the round-trip latency, the service name and version, and the per-dependency `checks` map that
`/ready` returns.

Nothing is simulated: "No answer" means no HTTP response arrived, "Reachable" means the server
answered, and "Reachable, but not ready" means it answered but reported a dependency as down. A
failed sign-in due to a transport error gains an inline hint pointing at this panel, so a wrong
address is never presented as a wrong password.

**What the address field accepts.** `192.168.1.5:8000` is not a URL — Dart reads `192.168.1.5` as
the *scheme*, so the request never leaves the app and the panel could only say "no answer". The field
therefore repairs a missing `http://` (for `localhost` and the private/link-local IPv4 ranges only;
a public host still has to be typed as `https://`, so the app can never silently downgrade real
traffic), drops any path and trailing slash (`…:8000/api/v1` would otherwise double the prefix), and
shows what was saved. Input that cannot be a base URL is rejected with a note and is not persisted.

**What a failure now says.** Under a failed `/health` probe the panel prints the reason and the next
step, never a bare code:

| Probe detail | What the panel says to do |
| --- | --- |
| `Connection refused` (or another OS message) | the device answered but the port is closed — start the API with `--host 0.0.0.0 --port 8000` |
| timed out after 8 s | the request was dropped rather than refused: firewall on the backend's machine, or a router keeping wireless clients apart |
| no response at all | nothing answered on that address and port — check the address, then the firewall |
| address unusable | type `http://<host>:<port>`, no path |

The panel also reads the phone's own IPv4 interfaces (one local, offline call, made when the sheet
opens — never on the button's path) and compares its /24 with the address typed. **Different network
is the most common cause of "no answer"** and is reported as exactly that, naming both sides:
*"This phone is on 10.0.0.7; the address typed is on 192.168.1."* When they match, the panel says so,
which rules the network out. When the platform reports no interfaces, it falls back to the firewall
advice rather than guessing. Every line ends with the pointer to the checklist in §4c, and with the
`/health` browser test that separates the two cases for good.

### 4b. Emulator

```bash
# terminal 1 — backend, bound beyond loopback
cd backend && ../.venv/bin/uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
# terminal 2 — app
cd mobile/flutter_app && flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000
```

`10.0.2.2` is the emulator's alias for the host machine. It is **not** an address any physical
device can use.

### 4c. Physical phone (the debug APK's case)

The phone and the development machine must be on the same network, and the app must be given the
machine's LAN address — `10.0.2.2` cannot work here.

```bash
bash scripts/lan_address.sh          # prints the LAN IPv4(s) and the exact commands to use

# 1) backend, reachable from the network, not just from this machine
cd backend && ../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

# 2) a debug build carries no fixed address, so nothing has to be rebuilt:
#    install the APK, then set http://<PC-IP>:8000 in the server panel (before sign-in)
#    and tap "Test connection".
#    To bake it in at build time instead:
cd mobile/flutter_app && flutter build apk --debug --dart-define=API_BASE_URL=http://<PC-IP>:8000
```

Checklist when the phone still cannot reach the backend:

| Symptom in the panel | Cause | Fix |
| --- | --- | --- |
| "No answer", instant | address typed wrong, or a typo in the port | re-read the address; `http://`, no trailing `/api/v1` |
| "No answer", after ~8 s | firewall on the development machine, or the backend bound to `127.0.0.1` | allow inbound TCP 8000; start uvicorn with `--host 0.0.0.0` (loopback-only cannot be reached) |
| "No answer" only from the phone, fine on the machine | phone on a different network, guest Wi-Fi, or client isolation / AP isolation on the router | join the same SSID; disable AP isolation; a phone hotspot with the machine joined works too |
| "No answer" while a VPN is active | the VPN owns the route | disconnect the VPN, or run the backend behind the VPN's reachable address |
| "Reachable, but not ready" | server is up, a dependency is down | read the `checks` lines (database, cache) — start Postgres/Redis |

`docs/development.md` has the same command for local API work; the phone tests the *same* server.

### 4d. Cleartext HTTP policy (why this bit debug builds)

`android/app/src/main/res/xml/network_security_config.xml` is the production policy: cleartext
permitted only for `10.0.2.2`, `localhost` and `127.0.0.1`, HTTPS everywhere else. A LAN address is
not knowable at build time, so **debug builds override it**: `android/app/src/debug/res/xml/
network_security_config.xml` permits cleartext to any host. That file lives in the `debug` source
set, so it is not compiled into a release APK or app bundle — the strict policy still governs
anything shipped.

A *release* build pointed at a LAN backend over plain HTTP therefore needs either HTTPS (the
production answer) or the specific host added to the `domain-config` list in the `main` policy. It
fails closed by design: a shipped build cannot silently send plaintext to an arbitrary host.

## 5. What the app does with credentials

* Access and refresh tokens live in `flutter_secure_storage` (Android Keystore-backed
  `EncryptedSharedPreferences`), never in `SharedPreferences`, logs or crash reports.
* `Session` is the only writer. A 401 triggers a **single-flight** refresh and one retry; a failed
  refresh clears the session and returns the user to sign-in.
* Nothing private is cached on disk. The only device-side caches are the tokens and the
  non-sensitive preferences (language, base-URL override).

## 6. Permissions declared

| Permission | Why |
| --- | --- |
| `INTERNET` | every screen reads from the API |
| `CAMERA` (`required="false"`) | photographing a diseased leaf for disease screening, or attaching a photo to a post; the gallery is also offered |

No location, contacts, storage or background permissions are requested: farms carry coordinates the
farmer enters, and weather is requested for those coordinates.

## 8. Known limitations (kept current)

1. **Only a debug APK is produced here.** No release keystore, no Play upload, no store listing.
2. **Push notifications are not delivered end to end.** The app can register a device token
   (`POST /notifications/devices`) and read in-app notifications, but no FCM/APNs credentials are
   configured, so pushes are not sent; the notification screen says so rather than implying push
   works.
3. **Demo providers are visible as demo.** Weather, market and LLM/embedding providers default to
   their mock implementations; the app renders the API's `is_demo`/`demo_notice` flags on every
   affected screen instead of presenting the values as live data.
4. **Disease screening is unavailable by default** because no trained artefact ships with the
   repository — the screen shows the backend's explanation.
5. **Icons, adaptive icon and splash are generated in-repo** (§3b), so they are placeholders in
   brand terms rather than in engineering terms: they are consistent and shippable, but a designer
   has not reviewed them. The privacy-policy / terms screens remain explicit placeholders, and no
   Play listing material (screenshots, descriptions) exists.
6. Localisation is a hand-maintained table for en/mr/hi (no ARB/codegen) — deliberate, and covered
   by a test that fails when a language is missing a key.
